# TradeXpress — Architecture

## Overview

TradeXpress is a simulated NGN-RMB (and multi-currency) cross-border trading
and settlement platform, built as an ongoing personal project rather than a
single finished deliverable. The primary goal is hands-on learning of new
technologies as they come up; recruiter/portfolio visibility is a secondary
benefit, not the driving priority. The project is designed to keep growing
indefinitely — new tech gets tried here as it's discovered, rather than the
project having a fixed end date.

Frontend work (Angular/TypeScript) is deliberately deferred until after major
backend modules are completed (e.g., all of Auth), not built alongside every
individual backend slice — this keeps focus on backend depth first while
still giving concrete, testable milestones to build a frontend against.

## Local Development Infrastructure

Supporting infrastructure runs locally via Docker Compose: PostgreSQL, Redis,
Kafka (KRaft mode), Kafdrop, with RabbitMQ planned for background job/task
processing (see "Messaging Strategy" below).

### PostgreSQL
- Primary datastore, used with EF Core Code-First.
- `postgres:16` image.
- Password authentication explicitly enforced via
  `POSTGRES_HOST_AUTH_METHOD=scram-sha-256` (the image defaults to "trust"
  auth otherwise). Auth method is fixed at first-time `initdb`, so changing
  it requires reinitializing the database from scratch.
- Data persists across container restarts via a named Docker volume
  (`postgres-data`).

### Redis
- Used for caching.
- `redis:7` image, password-protected via `--requirepass` (array-form command
  override, avoiding shell-parsing issues with special characters).
- Deliberately has no volume — cache data is disposable and rebuildable from
  Postgres, the correct mental model for a cache layer.

### Kafka (KRaft mode)
- Used for event-driven messaging (outbox pattern, pub-sub between
  consumers) for domain events: trades, settlement, KYC status changes,
  audit trail.
- `apache/kafka:3.7.0`, KRaft mode (no Zookeeper) — the modern approach;
  Zookeeper mode is being phased out industry-wide.
- Single node acts as both broker and controller
  (`KAFKA_PROCESS_ROLES=broker,controller`).
- **Dual-listener configuration**, required to solve a real Kafka-in-Docker
  problem: Kafka must advertise different addresses depending on who's
  connecting.
  - `PLAINTEXT` (`localhost:9092`) — for clients outside Docker (the .NET
    app on the host, DBeaver-style tools).
  - `INTERNAL` (`kafka:29092`) — for other containers on the same Docker
    network (Kafdrop) to reach Kafka via its service name.
  - Without this split, a container-based client connects via the service
    name, then gets told by Kafka to reconnect to `localhost` — which
    inside that other container means itself, causing a connection timeout
    loop. Hit and diagnosed directly during setup.
- Cluster ID auto-generated by the image on first run.

### Kafdrop
- Web UI for inspecting Kafka topics/partitions/messages.
- `obsidiandynamics/kafdrop`, connects via the `INTERNAL` listener
  (`kafka:29092`).

### Messaging strategy: Kafka vs. RabbitMQ
Fixed division of responsibility, decided once both tools' strengths were
compared directly:
- **Kafka** — outbox-driven domain events: trades, settlement, KYC status
  changes, audit trail. Anything multiple independent consumers may care
  about, treated as a permanent, replayable log.
- **RabbitMQ** (planned) — background job/task processing: KYC document
  pre-screening agent calls, webhook/notification retry logic. Leverages
  RabbitMQ's native dead-lettering and per-message TTL, which are more
  natural for "consumed once and done" work than replicating the same on
  Kafka.

## Solution Structure

Clean Architecture, five projects under `src/`, matching a Controllers /
Service / Repository mental model with different names:

TradeXpress.sln
├── src/
│ ├── TradeXpress.Domain/ — entities, enums (no dependencies)
│ ├── TradeXpress.Business/ — "Service" layer: MediatR commands,
│ │ handlers, validators, pipeline
│ │ behaviors, IApplicationDbContext
│ ├── TradeXpress.Data/ — "Repository" layer: EF Core
│ │ DbContext, Fluent API
│ │ configurations, migrations
│ ├── TradeXpress.Infrastructure/ — Kafka/RabbitMQ/Redis/external
│ │ service clients (not yet built out)
│ └── TradeXpress.Api/ — "Controllers" layer: controllers,
│ middleware, Program.cs, DI wiring
├── experiments/ — messier new-tech trial area
└── tests/ — unit + Testcontainers integration
tests (not yet built)


Dependency direction (strictly enforced): Domain has no dependencies.
Business depends only on Domain. Data and Infrastructure depend on Domain
and Business (implementing Business-defined interfaces). Api depends on
Business, Data, and Infrastructure.

**Critical rule:** Business never references Data directly. Business
defines abstractions (e.g. `IApplicationDbContext`); Data implements them.
This was violated once during early handler development (a handler
referenced `TradeXpressDbContext` directly) and corrected before it shipped
— worth remembering as the most likely mistake to make when adding new
handlers.

## Backend Request Flow (CQRS + MediatR)

Mapped explicitly onto the familiar Controller → Service → Repository → DB
pattern, since the terminology differs but the responsibilities don't:

| Familiar role | TradeXpress equivalent |
|---|---|
| Controller | ASP.NET Core Controller (e.g. `AuthController`) |
| DTO | The MediatR command itself (e.g. `RegisterIndividualCommand`), a `record` |
| IService | No single interface — MediatR's generic `IRequestHandler<TCommand,TResponse>` plays this role for every command |
| Service | The command's `Handler` class (e.g. `RegisterIndividualCommandHandler.Handle`) |
| IRepo | `IApplicationDbContext` (defined in Business) |
| Repo | `TradeXpressDbContext` (defined in Data, implements `IApplicationDbContext`) |

A request's actual path: Controller receives HTTP request → deserializes
body directly into a command record → `_mediator.Send(command)` → MediatR
resolves the command's type and dispatches through the registered pipeline
behaviors → `ValidationBehavior` runs first (see below) → if validation
passes, the command's `Handler.Handle(...)` runs → handler uses
`IApplicationDbContext` to persist changes → result flows back up through
the pipeline to the controller → controller returns the HTTP response.

**Why CQRS/MediatR over direct Controller→Service calls:** the deciding
factor was cross-cutting concerns (validation, and later caching, rate
limiting, idempotency) needing to apply uniformly to every command without
each handler remembering to invoke them manually. A MediatR pipeline
behavior wraps every command automatically; a plain service method would
require each method to call shared logic explicitly. The tradeoff is more
ceremony (three files per command: the command, its handler, its
validator) versus a single service method — accepted deliberately given how
many pipeline-behavior-worthy concerns are already planned across this
project.

**Files are organized by feature, not by technical layer** — e.g.
`Business/Auth/` holds `RegisterIndividualCommand.cs`,
`RegisterIndividualCommandHandler.cs`, and
`RegisterIndividualCommandValidator.cs` together, rather than a
project-wide `Commands/`, `Handlers/`, `Validators/` split. Company
registration will add three more files to the same `Auth` folder, following
the identical pattern.

## Validation

FluentValidation, wired through a generic MediatR pipeline behavior
(`ValidationBehavior<TRequest,TResponse>` in `Business/Common/`) rather than
called manually per-handler.

**Mechanism:** `ValidationBehavior` is registered once, as an open generic
(`IPipelineBehavior<,>` → `ValidationBehavior<,>`), so it applies to every
command automatically. At runtime, MediatR fills in the actual command type
(e.g. `RegisterIndividualCommand`) for that specific request, and the
behavior asks the DI container for every `IValidator<RegisterIndividualCommand>`
registered — `RegisterIndividualCommandValidator` matches, since
`AbstractValidator<RegisterIndividualCommand>` implements exactly that
interface. If any validator fails, the behavior throws `ValidationException`
and the request never reaches the handler.

Validators can depend on `IApplicationDbContext` for rules requiring a
database check (e.g. "is this email already taken") via FluentValidation's
`MustAsync`.

## Error Handling

Global exception-handling middleware (`Api/Middleware/ExceptionHandlingMiddleware.cs`)
wraps the entire request pipeline, catching:
- `FluentValidation.ValidationException` → clean `400 Bad Request` using
  ASP.NET Core's `ValidationProblemDetails` (RFC 7807 shape), with
  field-level error messages included (safe to expose).
- Any other unhandled exception → generic `500 Internal Server Error` using
  `ProblemDetails`, with **no internal exception details in the response**
  (deliberate — a raw EF Core/Postgres exception was confirmed to leak
  connection/schema details before this middleware existed). The real
  exception is logged server-side via `ILogger<ExceptionHandlingMiddleware>`
  (`LogWarning` for validation, `LogError` for everything else) so the
  cause is still discoverable without exposing it to the caller.

## Response Shape

Errors: `ProblemDetails` / `ValidationProblemDetails` (RFC 7807), matching
ASP.NET Core's own built-in conventions.

Success: no fixed envelope. Each endpoint returns whatever shape is natural
for that response (e.g. `{ "userId": "be40d95d-5a2b-4d22-ba23-3933364c9d2e" }`
for registration) — decided deliberately, not left unfinished. Standardizing
on `ProblemDetails` for all errors already gives API consumers (the future
Angular app) one consistent shape to branch on via HTTP status code; adding
a second wrapping envelope for success responses (`{ "data": {...} }`, or
Mukthar's usual `ResponseCode`/`ResponseMessage`/`Data` convention from other
projects) was considered and explicitly not adopted, since it would
duplicate information the status code and endpoint-specific response
already convey, for no real benefit in a solo-built API with one consumer.

## Database Migrations

EF Core Code-First, Fluent API only (no data annotations). Workflow: change
entity/configuration → `dotnet ef migrations add <Name>` → **open and read
the generated `Up()` method before applying** (a migration can silently
generate empty if the tool used a stale build — caught this once with
`AddUniqueEmailIndex`) → `dotnet ef database update`.

**Production migration strategy (decided, not yet implemented):** migrations
run as an explicit CI/CD step (GitHub Actions) before deploy, not
auto-applied on app startup — avoids race conditions across multiple
instances and lets a broken migration fail the deploy loudly rather than
crashing a live app.

## Secrets Management

- **Docker container credentials** (Postgres/Redis root passwords): stored
  in a gitignored `.env` file, referenced in `docker-compose.yml` via
  `${VARIABLE_NAME}` substitution. Protects the containers themselves.
- **Application connection strings** (what the .NET app uses to reach those
  same containers): stored via `dotnet user-secrets`, **not** in
  `appsettings.Development.json` (which is committed to Git).
  `appsettings.Development.json` keeps the config *shape* present with
  empty values, so the file documents what's expected without leaking
  anything. User Secrets is local-machine-only by design — moving to a new
  machine means re-running `user-secrets set` with real values again; it
  does not sync anywhere, which is intentional.
- **Production:** connection strings set as real environment variables on
  the hosting platform (Render/Railway), e.g.
  `ConnectionStrings__DefaultConnection` (double underscore = .NET's env-var
  translation of the colon in nested config keys). Same
  `builder.Configuration.GetConnectionString(...)` call works unchanged
  across dev/prod, since the app never needs to know which config source a
  value came from.

## Known Issues / Gotchas

- **Swagger UI "invalid version field" error**: newer .NET SDK versions
  generate OpenAPI specs with `"openapi": "3.0.4"`, but older bundled
  `swagger-ui-dist` builds (inside older `Swashbuckle.AspNetCore` versions)
  reject that version string as invalid, even though it's valid OpenAPI.
  Fixed by updating `Swashbuckle.AspNetCore` to a current version
  (`10.2.3`+, tracked upstream as GitHub issue "Add support for OpenAPI
  3.0.4"). **If this resurfaces after a future package update, also check
  for a stale browser cache** — `swagger-ui-bundle.js`/`swagger-ui.css`
  loading from memory cache masked the fix working on first reload; a
  hard, cache-disabled reload (DevTools → Network → "Disable cache") is
  the reliable way to confirm.
- **MediatR licensing**: recent MediatR versions (v13+) display a startup
  warning (`LuckyPennySoftware.MediatR.License`) about requiring a paid
  license for commercial/production use. Harmless for this
  personal/portfolio project; would need addressing (paid license, or
  switching to an MIT-licensed alternative/hand-rolled dispatcher) if
  TradeXpress ever became a commercial product.

## Git / GitHub

Repository is public on GitHub, pushed with full incremental commit
history intact (not a single bulk upload) — the goal is that an
interviewer sees genuine periodic progress over time, not one dump.
Commits happen at natural completion points (a working migration, a
verified endpoint, a fixed bug), following the same discipline used
throughout local development.
