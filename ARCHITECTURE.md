# TradeXpress — Architecture

## Overview

TradeXpress is a simulated NGN-RMB (and multi-currency) cross-border trading
and settlement platform, built as an ongoing personal project rather than a
single finished deliverable. The primary goal is hands-on learning of new
technologies as they come up; recruiter/portfolio visibility is a secondary
benefit, not the driving priority. The project is designed to keep growing
indefinitely — new tech gets tried here as it's discovered, rather than the
project having a fixed end date.

## Local Development Infrastructure

The project runs its supporting infrastructure locally via Docker Compose,
with four services: PostgreSQL, Redis, Kafka (KRaft mode), and Kafdrop.

### PostgreSQL
- Primary datastore, used with EF Core Code-First.
- Runs on the official `postgres:16` image.
- Password authentication is explicitly enforced via
  `POSTGRES_HOST_AUTH_METHOD=scram-sha-256`. By default, the Postgres Docker
  image uses "trust" authentication for local connections, meaning no
  password is actually required — this had to be set deliberately and
  required reinitializing the database from scratch, since auth method is
  only configured once, during first-time `initdb`.
- Data persists across container restarts via a named Docker volume
  (`postgres-data`), mapped to Postgres's internal data directory. Without
  this, all data would be lost every time the container is removed.

### Redis
- Used for caching.
- Runs on the official `redis:7` image.
- Password-protected via `--requirepass`, passed as a command override in
  array form (safer than a plain string, since it avoids shell parsing
  issues with special characters in the password).
- Deliberately has **no** volume — cache data is treated as disposable and
  rebuildable from the source of truth (Postgres), which is the correct
  mental model for a cache layer.

### Kafka (KRaft mode)
- Used for event-driven messaging (outbox pattern, pub-sub between
  consumers).
- Runs on the official `apache/kafka:3.7.0` image, using KRaft mode rather
  than the older Zookeeper-based setup. KRaft removes the need for a
  separate Zookeeper container by having Kafka manage its own cluster
  metadata internally — it's the modern, forward-looking approach, and
  Zookeeper mode is being phased out industry-wide.
- Single-node setup: one node acts as both broker (handles data) and
  controller (manages cluster metadata), configured via
  `KAFKA_PROCESS_ROLES=broker,controller`.
- **Dual-listener configuration** was required to solve a real Kafka-in-Docker
  problem: Kafka needs to advertise different addresses depending on who's
  connecting.
  - `PLAINTEXT` listener (`localhost:9092`) — for clients outside Docker
    (the future .NET app running on the host machine, DBeaver-style tools).
  - `INTERNAL` listener (`kafka:29092`) — for other containers on the same
    Docker network (e.g. Kafdrop) to reach Kafka using its service name.
  - Without this split, a container-based client (like Kafdrop) would
    initially connect fine via the service name, but then be told by Kafka
    to reconnect to `localhost` — which inside that *other* container means
    itself, not the Kafka container — causing a connection timeout loop.
    This was hit and diagnosed directly during setup.
- Cluster ID is auto-generated by the image on first run rather than
  manually specified, which is the simpler path for a single-node local
  cluster.

### Kafdrop
- Web UI for inspecting Kafka topics, partitions, and messages, so Kafka's
  behavior is visible rather than a black box.
- Runs on `obsidiandynamics/kafdrop`, connects to Kafka via the `INTERNAL`
  listener (`kafka:29092`), since it's a container-to-container connection
  on the same Docker network.

## Local Tooling
- **VS Code** with the C# Dev Kit extension for development and debugging.
- **Docker Desktop** to run the Compose stack.
- **DBeaver** for inspecting Postgres directly.
- **RedisInsight** for inspecting Redis keys/data.
- **Thunder Client** (or Postman) for manual API testing.
- **dotnet-ef** global tool for EF Core migrations.

## Security Notes (local dev)
- All local service credentials are stored in a `.env` file (gitignored,
  never committed) and referenced in `docker-compose.yml` via variable
  substitution (`${VARIABLE_NAME}`), rather than being hardcoded directly
  in the compose file. This keeps no credential values — even fake local
  ones — anywhere in version control history.
- These are local-only development credentials and are never reused for
  cloud/production credentials (Neon/Supabase, etc.).
